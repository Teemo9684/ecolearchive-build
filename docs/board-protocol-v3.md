# v3 experimental push extension
Android listens on UDP 8767 for TABSI_BOARD_DISCOVER_V3 <base64 challenge>, responds JSON {challenge,id,name}. TCP HTTP 8766 /board/pair/start (commit), /pair/reveal (session,public,nonce), /pair/finish (session,proof), /push (revision,sha256,blob). P-256 uncompressed SEC1 public keys, 32-byte nonces. Commitment SHA256("tabsi-pair-v3" || PC pub || PC nonce). Transcript SHA256(domain || PC pub || PC nonce || TV pub || TV nonce || session UTF8). secret=HMAC-SHA256(ECDH shared X, transcript). SAS first 4 bytes big-endian HMAC(secret,"sas") mod 1000000; six digits displayed on TV and entered on PC, never sent. PC proof HMAC(secret,"pc-confirm"), TV proof HMAC(secret,"tv-confirm"). Master=HMAC(secret,"board-master-v3"); AES key=HMAC(master,"aes"), receipt key=HMAC(master,"ack"). Push blob IV12 + AES-GCM ciphertext/tag16, AAD ecolearchive-board-v2. Receipt proof HMAC(ack, UTF8 "activated\n"+revision+"\n"+sha256). Device must verify/decrypt/store/activate before receipt, handle repeat revision with identical plaintext and fresh ciphertext, reject stale approval date. Manual fallback IPv4. No archive endpoints. This is a trial protocol requiring interoperability and security review before production.

Android must show the six-digit SAS and require local user consent for the pending session before finish. PC retries discovery and delivery every 30 seconds while running; only authenticated activation proof updates success. Repeated approved revisions must not reset the active display. Pairing key and last receipt stored via DPAPI, Android Keystore for AES/HMAC. No public update publication in 1.0.50 test workflow.
